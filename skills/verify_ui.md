# Skill: Verify UI（ブラウザ動作確認の方針）

Web アプリの動作確認は、**モデル推論を伴うブラウザ操作ループを既定にしない**。
「スクリーンショットを撮る → 判断する → 操作する」の繰り返しは毎ステップ画像をモデルに送るため、
どの CLI で行っても高コストであり、サイクルのたびに全ステップが再実行される。

## 原則：一度スクリプトに落とし、以後は推論なしで回す
1. **spec を書く** — Playwright（既存の E2E フレームワークがあればそれ）の spec を `src/` 配下（または既存のテストディレクトリ）に置く。**spec の生成は Codex へ委譲する**（コード生成のため `agents.md` のルーティング規約に従う）。
2. **実行する** — `npx playwright test` 等をコマンドとして実行する。Antigravity が直接実行してよい（モデル推論を伴わないためトークンを消費しない）。
3. **失敗時のみモデルに渡す** — 失敗したケースのログと該当ステップのスクリーンショットだけを **Claude Code へ委譲**して原因分析させる。全ステップ・全画面を渡さない。

## 対話的なブラウザ操作を使ってよい場合（例外）
次の 2 つに限る。使った場合は**操作ステップ数を journal に記録する**。
- spec が 1 本も無い初回の疎通確認（画面が出るか／主要導線が通るか）を **1 回だけ**
- 自動化が困難な視覚判断（レイアウト崩れ、描画の乱れなど）

**同じ確認を 2 回以上行うなら、必ず spec に落としてから実行する。** 手作業での再確認の繰り返しは規約違反として扱う。

## 記録（必須）
`track_progress.md` に従い、次を journal に残す。
- 実行した spec とその結果（passed / failed の件数）
- **ブラウザ操作ステップ数**（対話操作を行った場合。0 なら 0 と書く）
- spec 化せずに対話操作で済ませた場合はその理由

ブラウザ操作ステップ数は `manage_quota.md` の台帳で「Gemini 自前処理」として計上する。
